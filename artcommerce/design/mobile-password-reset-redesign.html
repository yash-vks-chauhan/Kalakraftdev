Password reset · mobile viewport

Three page loads to change one password.

Resetting a password is currently three routes — /forgot-password, /sent, then /verify — and the middle one exists only to say the email is coming. Meanwhile the code that expires in five minutes never shows a clock, and the address it was sent to has to be typed again on the last screen. This is that flow rebuilt for a phone, on the same shell the sign-in screens now use. The prototype is live.

One screen, four panes, no navigation

03 — Findings

Eight things to change, and what replaces each

01

It no longer matches sign-in

The reset screens kept the old brand strip while /auth/login moved to the crown-and-sheet layout. Arriving here from Forgot password? now feels like leaving the site.

The same shell, one size down

The crown at 168 px rather than 230 — this is a task, not a welcome — and no rotating hero. Same gradients, same sheet, same sticky bar.

02

A whole screen to say "we sent it"

/sent renders a banner, a card repeating what the banner said, and two buttons — one of which just goes back a step. It costs a page load and tells the person nothing they didn't know.

Fold it into the code pane

Sending advances straight to the code entry, with the address shown at the top and the resend control on the same screen. The confirmation is the pane change.

03

Same mobile problems as the old sign-in

Top-aligned form in h-svh, dead space below, a CTA in normal flow that the keyboard can bury.

Crown, sheet, sticky bar

Exactly what the sign-in screens got, including the visualViewport keyboard inset — AuthShell already supports it behind mobileCrown.

04

The email is typed twice

The last screen shows an editable email field, prefilled from a query param. Edit it — or lose the param — and the code silently stops matching, which reads as "wrong code".

Show the address, don't ask for it

The email the code went to sits at the top of the pane as a chip with a Change control that returns to step 1. It can't drift out of sync with the code.

05

The step rail costs more than it gives

A bordered three-segment rail plus a "Step 2 of 3 · …" caption takes about 70 px on every screen to say what the heading already says.

A 3 px rail and a mono line

Three hairlines under the grabber, filling as you go, plus Step 2 of 3 as the pane's eyebrow. Same information, about 60 px cheaper.

06

Resending means going backwards

"Resend code" is a link back to step 1, where the form must be submitted again. There is no confirmation that a new code went out, and nothing prevents hammering it.

Resend in place, with a cooldown

One control on the code pane. It sends, confirms inline, restarts the clock, and greys out for 30 seconds — visible rate limiting instead of silent 429s.

07

A six-character code in a plain text box

The field does the basics right — it uppercases, strips spaces and asks for one-time-code autofill. What it doesn't do is show how many characters are wanted, and it accepts maxLength={8} for a code the API generates at exactly six. At 16 px with letter-spacing, a mistyped character is hard to spot.

Six boxes — the count is the affordance

22 px mono in 56 px boxes, auto-advancing, backspace stepping back, a pasted code spreading across all six, and the one-time-code hint kept on the first. Submits itself on the sixth character, so verifying costs no taps.

08

The clock is invisible, and so is strength

Codes die after five minutes and nothing counts down — an expired code just returns an error. And this screen sets a password with no strength meter, while sign-up has one.

A live countdown and the sign-up meter

The clock ticks on the code pane, turns amber under a minute, and at zero swaps itself for a resend. The password pane reuses PasswordStrength and the requirement chips already in AuthBits.

04 — The code's five minutes

What the person should see, minute by minute

OTP_EXPIRY_MS is five minutes and the alphabet deliberately drops I, O, 0 and 1. Today none of that reaches the screen. This is the state the code pane should be in across that window.

5:00 — 1:00

Running

Neutral row: Code expires in 4:12. Resend is available but quiet — most people never need it.

0:59 — 0:01

Running out

The row turns amber and the number takes the accent. No modal, no bounce — just enough to say hurry or resend.

0:00

Expired

Boxes clear and disable, the row goes red and reads Code expired, and Resend becomes the primary thing on the pane.

after resend

Cooling down

New code sent confirms inline, the clock restarts at 5:00, and Resend greys for 30 seconds so the rate limit is visible before it bites.

05 — Routing

Every URL that works today keeps working

The flow collapses into panes, not into a single URL. Emailed links point at /confirm?token=, so that route has to keep resolving — it opens the code pane, or skips straight past it when the link already carries the code.

URLTodayProposedNote
/forgot-password Email form Opens pane 1 ?email= prefills as it does now
/forgot-password/sent Interstitial Opens pane 2 Kept as a redirect so back-button history stays valid
/forgot-password/verify Code + password Opens pane 2 Skips to pane 3 when ?otp= is present and valid
/forgot-password/confirm Code + password Opens pane 2 The address in reset emails — ?token= fills the six boxes
/auth/login?reset=1 Success banner Unchanged Where pane 4 lands, with the email carried over

Built from what exists

  • AuthShell — pass mobileCrown, actionBar; add a crownSize of "compact"
  • PasswordStrength, PasswordRequirements, Banner, EmailInput — all already in AuthBits
  • OtpInput is the one new primitive; nothing to install
  • ResetFlow.tsx mirrors AuthFlow.tsx: one client component, panes inside

Accessibility

  • Six boxes are one labelled group; each has its own aria-label
  • The countdown is aria-live="off" — a per-second announcement would be unusable — with a polite announcement at 1:00 and at expiry
  • Errors are role="alert"; pane changes move focus to the new heading
  • Every control clears 44 px; boxes are 56 px tall

Unchanged on purpose

  • No API changes — same two endpoints, same payloads
  • The neutral response ("if an account exists…") stays; enumeration is still not possible
  • The desktop layout, as before, is untouched
  • Code length and alphabet stay server-owned; the UI just stops contradicting them
